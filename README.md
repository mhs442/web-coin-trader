# Web Coin Trader

Bybit API 기반 암호화폐 자동매매 웹 애플리케이션

## 주요 기능

- **실시간 대시보드** - 전체 코인 시세 목록 (1초 갱신, 거래량 기준 정렬)
- **상세 차트** - 코인별 캔들 차트 (1분/5분/15분/30분/1시간) + 호가창
- **패턴 기반 자동매매** - 큐 > 단계 > 패턴 > 블록 계층 구조로 매매 전략 구성
- **거래량 급변 시 큐 중지** - 진입 시점 대비 최근 60초 체결량이 급감·급증하면 현재 단계 종료 후 큐 중지 (큐별 선택)
- **마이페이지** - 거래 히스토리 조회, 패턴 관리
- **회원가입/로그인** - Bybit API Key 검증 포함

## 자동매매 거래 플로우

> 기준 코드: `common/autotrade/service/AutoTradeService.java` (엔진), `common/trade/service/TradeFacade.java` (MAIN/SIM 분기),
> `bybit/trade/BybitTradeClient.java`, `binance/trade/BinanceTradeClient.java` (거래소 주문).
> 문서 작성일: 2026-10-29

### 1. 기본 개념

| 용어 | 설명 |
|---|---|
| 큐 (PatternQueue) | 자동매매 전략 1개. **사용자·거래소·심볼·모드(MAIN/SIM)당 1개만** 등록 가능 (코드 `EXCEED_MAX_QUEUES` + DB UNIQUE) |
| 단계 (step) | 1~20단계, 번호는 1부터 연속. 손절 시 다음 단계로 이동 |
| 패턴 (Pattern) | 단계당 정확히 2개 — LONG으로 시작하는 패턴 1개 + SHORT로 시작하는 패턴 1개. 레버리지·투자금(마진)·익절률·손절률 보유 |
| 블록 (block) | 패턴 = 조건 블록들 + 마지막 **leaf 블록**. 조건 블록은 1분봉 방향(L/S)과 맞는지 판단, leaf 블록 도달 시 진입 |
| 진입 방향 | **leaf 블록의 side** (첫 조건 블록 방향이 아님). 예: `S:L` 패턴은 SHORT 신호로 시작하지만 LONG 진입 |
| 세션 | (사용자, 거래소, 심볼, 모드)별 실행 단위. 활성 큐가 있으면 생성, 없으면 제거 |
| 모드 | MAIN = 실거래(거래소 주문), SIM = 모의투자(가상 지갑, 거래소 주문 없음) |

큐 등록 검증: 거래 가능한 심볼, 트리거 변동률 > 0, 단계별 패턴 2개·시작 블록 방향 중복 금지, 단계 번호 연속.
활성화된 큐는 수정할 수 없습니다 (매매 중 구조 변경 방지).

### 2. 이벤트 입력과 세션 레인 (동시성 모델)

[사용자 정책 2026-10-29] **하나의 동작은 이전 동작이 거래소에서 완료 확인된 뒤에만 시작한다.**
이를 위해 세션마다 처리 스레드를 하나로 직렬화한 "세션 레인"을 둡니다.

```
[WS tickers push] ─┐ latestPrice(최신값만 유지)
[1초 REST tick]  ──┤   (해당 거래소 WS 비활성 시에만)
[WS kline confirm]─┤ pendingKlines (전부 순서대로)
[private 청산 체결]─┤ pendingCloses (외부 청산)
[30초 재조정]    ──┤   (놓친 외부 청산 → pendingCloses 로 합류)
[큐 끄기·삭제 API]─┘ pendingCommands (사용자 명령)
                     │
                     ▼  scheduleLane: 세션당 동시에 1개 작업만 실행
               drainLane 루프 (한 바퀴 순서)
                 0) pendingCloses  → processExternalClose
                 0-1) pendingCommands → closeQueuePositionInLane
                 1) pendingKlines  → applyKlineSignal (봉당 1회)
                 2) latestPrice 1개 → processQueue (페이즈별 처리)
                 → 처리마다 STOMP 상태 push
```

- WS 수신 스레드는 값만 넣고 즉시 반환합니다. 주문·조회 대기는 모두 레인 스레드에서 일어납니다.
- 외부 청산을 가장 먼저 처리해, 이미 닫힌 포지션에 가격 기반 매도/청산 주문을 내지 않습니다.
- 레인 종료 직전에 들어온 값이 있으면 다시 제출합니다 (누락 방지). 실행 대기가 3초 이상이면 경고 로그.
- 세션이 끝난 뒤에도 남은 사용자 명령은 실행해 응답을 기다리는 요청을 완료시킵니다.

### 3. 큐 상태 전이

```
TRIGGER_WAIT ──(기준가 대비 ±triggerRate% 변동)──▶ BLOCK_MATCHING ──(leaf 도달)──▶ POSITION_HOLDING
     ▲                                                  ▲   ▲                             │
     │ 모든 단계 소진 + cycle=true                       │   │ 익절: 1단계·같은 방향          │
     └──────────────────────────────────────────────────┼───┴───────────────────────────────┤
                                                        │ 손절: 다음 단계·반대 방향          │
                                                        └───────────────────────────────────┘
                     모든 단계 소진 + cycle=false → 큐 비활성화
```

#### 3-1. TRIGGER_WAIT
1. 첫 가격을 기준가로 저장합니다.
2. 이후 변동률 ≥ `+triggerRate` → LONG, ≤ `-triggerRate` → SHORT 신호.
3. 현재 단계에서 첫 조건 블록이 신호 방향인 패턴을 선택하고, 첫 블록은 매칭된 것으로 간주해 **2번째 블록부터** 매칭합니다.

#### 3-2. BLOCK_MATCHING
- **조건 블록**: 가격 push 시에는 관찰 시작 시각만 기록하고, 판단은 거래소 1분봉 마감 push(`confirm:true`)에서만 합니다 (서버 시계 사용 안 함).
  - 봉의 `close > open` → LONG, `close < open` → SHORT, 같으면(도지) 다음 봉 재대기.
  - 신호 일치 → 다음 블록. 신호 반대 → 같은 단계의 반대 방향 패턴으로 전환(2번째 블록부터).
  - 기준 시각이 2분 넘게 갱신되지 않으면(봉 마감 누락) 현재 시각으로 재대기.
- **leaf 블록**: 도달 즉시 가격 push에서 진입(`openPosition`).

#### 3-3. 진입 (openPosition) — 시장가
1. 이중 진입 방지: `entryPrice`가 있으면 무시. 주문 전 `entryPrice` 선점.
   - **기존 포지션 확인 (MAIN)** [사용자 정책 2026-10-29]: 주문 전에 거래소 포지션을 조회해, 이미 포지션이 있거나 조회에 실패하면
     주문하지 않고 **같은 단계의 TRIGGER_WAIT로 복귀**(로그 `[진입 보류]`, 큐는 활성 유지). 재시작 전에 남은 포지션 위에 진입하는 것을 막습니다.
2. 수량 = 마진 × 레버리지 / 현재가 → qtyStep 단위. 0이면 스킵(5회 연속 시 큐 비활성화).
3. 마진 모드 Isolated 전환 → 레버리지 설정. 실패 시 FAILED 이력 + 큐 비활성화 (이전 레버리지로 진입하지 않음).
4. 시장가 진입 주문 (`clientOrderId = q{큐ID}-E-{ms}`) + **거래소 안전망 TP/SL 동봉**
   - 앱 TP/SL보다 가격 기준 0.5%p 바깥 → 정상 상황에서는 앱이 먼저 청산, 서버 장애 시에만 거래소가 청산.
   - Bybit: 주문 필드로 동봉 / Binance: 진입 후 조건부(algo) 주문 `TAKE_PROFIT_MARKET`/`STOP_MARKET` 별도 등록, 진입 전 심볼의 기존 조건부 주문 전부 취소.
   - tickSize 조회 실패 시 TP/SL 생략, 손절률이 강제청산 한도(`100 - 1.5 × 레버리지`) 초과면 SL만 생략, SHORT 익절가 ≤ 0이면 TP만 생략.
5. 실체결가·실수수료 조회 (WS 체결 우선 → REST). **조회 실패(MAIN) 시 거래소 포지션 수량으로 확인**:
   - 포지션 0 → 진입 미체결: FAILED 이력 + 큐 비활성화.
   - 조회 실패 → `pendingConfirmType=ENTRY` 확인 대기 (이력 저장 보류, TP/SL 판단 보류).
6. 진입 이력 저장(실패해도 진입은 성공으로 유지 — fallback 이력만 남김).
7. 실체결가 기준 TP/SL 가격 계산 → `POSITION_HOLDING` 전환.
8. 진입이 확인된 경우에만 **익절 지정가 등록** (아래 3-4).

TP/SL 가격: `진입가 × (1 ± 비율 / (100 × 레버리지))`. 비율은 투자금(ROI) 기준 %, 미입력 시 가격 8%(= 8 × 레버리지 %).

#### 3-4. 익절 지정가 (MAIN) — 수수료 절감
진입 체결 직후 TP 가격에 **reduceOnly 지정가(GTC)** 를 호가창에 걸어 maker(0.02%)로 익절합니다. 진입·손절은 시장가(taker) 유지.

- 가격: TP 가격을 tickSize로 맞춤 (LONG 매도는 올림, SHORT 매수는 내림 — 목표가보다 불리하지 않게).
- `clientOrderId = q{큐ID}-T-{ms}` → 체결 이벤트 매칭·취소 키.
- Binance는 지정가 접수 후에도 포지션이 남아 있으므로 안전망 조건부 주문을 취소하지 않습니다.
- PostOnly 미사용: 등록 순간 이미 TP를 넘었으면 즉시 체결(taker)되어 정상 익절 처리.
- **등록 실패 (D2)**: FAILED 이력(`[익절 지정가 등록 실패] 사유`) → 혹시 접수됐을 지정가 취소 → 포지션 시장가 청산(LIQUIDATION 이력) → 큐 비활성화.
- **SIM**: 주문 없이 같은 지정가만 미리 계산. 가격이 TP에 닿으면 체결가 = 지정가, 수수료 = maker로 기록.

#### 3-5. POSITION_HOLDING (가격 push마다)
| 상황 | 동작 |
|---|---|
| 진입·청산 확인 대기 중 | 신규 주문 없이 1초 간격으로 거래소 포지션만 재확인 |
| TP 도달 + 익절 지정가 있음 (MAIN) | 아무것도 안 함 — 거래소 체결 이벤트를 기다림 |
| TP 도달 + 지정가 없음 (SIM) | `handleSellSuccess`: 매도 이력 → 청산 확인 → 1단계 리셋 |
| SL 도달 + 지정가 없음 | `handleLiquidation`: reduceOnly 시장가 청산(`q{큐ID}-L-{ms}`) → 확인 → 다음 단계 |
| SL 도달 + 익절 지정가 있음 | `handleStopLossWithTpLimit` (아래) |

**손절 시 익절 지정가 처리 (`handleStopLossWithTpLimit`)**
1. 익절 지정가 취소. 결과가 `CANCELLED`/`NOT_FOUND`가 아니면 이번 손절 보류 → 1초 뒤 재시도, 5회 연속 실패 시 큐 비활성화 + 수동 확인 안내.
2. 취소 후 거래소 잔여 포지션 조회.
   - 0 → 이미 익절 체결로 닫힘: 시장가 손절 생략, 거래소 청산 내역 기준으로 처리.
3. 익절 체결 수량 = 진입 수량 − 잔여 수량.
   - 0 → 전량 시장가 손절 (기존 흐름).
   - \> 0 → **부분 익절 후 손절 (D1)**: 잔여 수량만 시장가 청산. 레인 안에서 추정 손익으로 즉시 판단
     - 익절분 = (지정가 − 진입가) × 체결수량 × 방향 − maker 수수료, 손절분 = (현재가 − 진입가) × 잔여수량 × 방향 − taker 수수료
     - [사용자 정책 2026-10-29] **합산 ≥ 0 → 익절 경로**(1단계·같은 방향), **< 0 → 손절 경로**(다음 단계·반대 방향)
     - 거래 이력 2건(부분 익절 SELL + 잔여 LIQUIDATION), 투자 이력은 1건(가중평균 청산가, 두 수수료 합산).

#### 3-6. 청산 완료 확인 (MAIN)
[사용자 정책 2026-10-29] 매도/청산 주문 접수 후 **거래소 포지션 0을 확인한 뒤에만** 다음 상태로 전환합니다.
- 미확인(조회 실패·포지션 잔존) → `POSITION_HOLDING` 유지 + 청산 확인 대기, 1초 간격 재확인(신규 주문 금지).
- 5회 연속 미확인 → 큐 비활성화 + "거래소 포지션을 수동으로 확인" 안내.
- SIM은 즉시 완료.
- 청산 주문이 거부됐는데 포지션이 이미 0이면(외부에서 닫힘) 진입 이후 청산 내역을 조회해 외부 청산 규칙으로 처리.

#### 3-7. 외부 청산 (거래소 안전망 TP/SL, 강제청산, 수동 청산, 익절 지정가 체결)
- 거래소 private 스트림의 청산 체결 → `pendingCloses` → 레인에서 처리. 앱이 낸 `-S-`/`-L-` 주문 체결은 무시.
- **30초 재조정**: 보유 큐가 있는 MAIN 세션의 포지션을 30초마다 확인, 0이면 진입 이후 마지막 청산 내역을 조회해 같은 경로로 처리 (WS 끊김 대비).
- 처리 전 거래소 포지션 재확인: 조회 실패면 경고 후 대기, 포지션 남아 있으면 무시.
- 청산 방식 판정:

| 판정 | 결과 |
|---|---|
| `orderLinkId == 익절 지정가 ID` | **TAKE_PROFIT 확정** (일반 지정가는 거래소 분류가 OTHER일 수 있어 ID로 판정) → 1단계 리셋, maker 추정 수수료 |
| 거래소 TP | 1단계 리셋 (SELL 이력) |
| 거래소 SL / 강제청산 | 다음 단계·반대 방향 (LIQUIDATION 이력) |
| 그 외 (ADL·수동 등 OTHER) | 큐 비활성화 |

- 익절 지정가 외의 방식으로 닫혔는데 지정가가 남아 있으면 취소합니다(다음 진입 포지션을 줄이지 않도록). 취소 실패 시 큐 비활성화.
- 청산 확인 대기 중인 큐는 외부 청산 처리에서 제외 (확인 로직이 전환).

#### 3-8. 큐 끄기·삭제 시 보유 포지션 청산 (D4)
[사용자 정책 2026-10-29]
1. 화면: 보유 중인 큐를 OFF/삭제하면 확인 팝업. 취소 시 요청 안 보냄.
2. 서버(`AutoTradeController` → `AutoTradeService.closeQueuePosition`): **팝업과 무관하게 항상** 청산 먼저 수행.
   - 세션 레인에 명령을 넣고 최대 30초 대기 (틱 처리와 경쟁하지 않음).
   - 보유 중이 아니면 바로 진행. 진입 확인 대기 중이면 "잠시 후 다시 시도" 오류.
   - 익절 지정가 취소(실패 시 오류) → 잔여 수량 확인(MAIN은 거래소 포지션, SIM은 진입 수량) → 부분 익절분 기록 → **잔여 전량 reduceOnly 시장가 청산**(이력 라벨 "청산(큐 종료)").
   - 거래소 포지션 0 확인 → 큐를 세션에서 분리 → DB 비활성화/삭제.
3. **청산 실패 시 큐 유지** + 400 오류 `"포지션 청산에 실패해 큐를 유지합니다: 원인"` → 화면 알림.
   - 청산 주문은 접수됐으나 포지션 0이 아직 확인되지 않으면 오류를 반환하고, 이후 틱에서 확인되면 엔진이 큐를 자동 비활성화합니다.

#### 3-9. 거래량 급변 시 큐 중지 (큐별 선택, MAIN·SIM)
[사용자 정책 2026-10-29] 큐의 `volume_stop_enabled`가 켜진 경우에만 동작합니다.
1. **집계** (`VolumeMonitorService`): 감시를 켠 큐가 활성인 심볼만 체결 스트림 구독 — Bybit `publicTrade.{symbol}`, Binance `{symbol}@aggTrade`.
   최근 60초 체결량(코인 수량)을 1초 버킷 60개로 합산합니다. 구독 후 60초가 지나야 값이 나옵니다(워밍업).
2. **기준**: 진입 시점의 60초 체결량. 워밍업 중 진입이면 창이 다 찬 첫 시점의 값으로 확정합니다(B안 — 값 튐 방지).
3. **감지** (POSITION_HOLDING, 가격 push마다): 현재 / 기준 ≤ 0.5 → 급감, ≥ 1.5 → 급증. 기준이 0이면 판정하지 않습니다.
4. **예약** (1회): DB `volume_stop_reason`에 사유 저장(단일 컬럼 UPDATE). **포지션은 유지**하고 현재 단계는 TP/SL대로 진행합니다.
   - 사유 예: `[거래량 급감 중지] 감지 14:03:21 · SHORT 보유 · 진입 기준 120.5 → 52.1 (-56.8%)`
5. **중지**: 익절·손절로 단계가 끝나는 시점(`resetToFirstStepAfterSell` / `moveToNextStepAfterLiquidation` 맨 앞)에
   다음 단계로 가지 않고 STOP 이력 저장 → 큐 비활성화 → 예약 해제. 자동 재개는 없습니다.
- 예약 중 사용자가 끄기·삭제: 3-8 흐름(청산 후 종료), STOP 이력 없음. 사용자가 켜기·끄기를 하면 예약은 해제됩니다.
- 앱 재시작 후에는 예약을 따로 처리하지 않습니다(세션은 처음부터 다시 수행).

### 4. 이력 저장

| 테이블 | 시점 | 내용 |
|---|---|---|
| 거래 이력 (trade_history / sim_trade_history) | 진입·매도·청산·실패·큐 중지 | 주문 1건당 1행. ENTRY / SELL / LIQUIDATION, SUCCESS / FAILED, 실체결가·실수수료, 오류 사유. 거래량 급변 중지 시 **STOP** 1행(주문 없음, amount 0, 중지 시점 가격, 사유는 error_message) |
| 투자 이력 (investment_history / sim_investment_history) | 사이클(진입→청산) 완료 | 진입가·청산가·마진·레버리지·예상 TP/SL가·손익·펀딩비 |

- 청산 이력은 **비동기 후처리**(`closeRecordExecutor`)로 저장 → 매매 흐름을 막지 않음. 상태 전환 전 진입 정보를 스냅샷(`CloseRecord`)으로 넘김.
- MAIN 손익: 거래소 실손익(펀딩비 포함, closed-pnl) 우선, 조회 실패 시 계산식. 부분 익절 합산 건은 계산식(펀딩비 없음).
- SIM 손익: 계산식. 진입 시 지갑에서 마진·진입 수수료 차감, 청산 시 마진 + 손익 − 청산 수수료 반영.
- **fallback** [사용자 정책 2026-10-29]: 이력 저장 실패 시 `log.error` + 거래 이력에 FAILED 행(`[이력 저장 실패] 체결은 완료됨 — 원인`) 저장. fallback마저 실패하면 에러 로그만.
- 거래소 거부(ORDER_FAILED)·마진 모드·레버리지 설정 실패도 FAILED 이력으로 기록 (거래소 응답 `[code] msg` 포함).

### 5. 수수료

| 구분 | 주문 | Bybit | Binance |
|---|---|---|---|
| 진입 | 시장가 | taker 0.055% | taker 0.05% |
| 익절 | 지정가 GTC | maker 0.02% | maker 0.02% |
| 손절·큐 종료 청산 | 시장가 | taker 0.055% | taker 0.05% |

추정 수수료 = 체결가 × 수량 × 요율 (소수 4자리). MAIN은 실체결 수수료가 조회되면 그 값으로 저장.

### 6. 큐 비활성화 조건 (자동)
진입 수량 0 연속 5회, 마진 모드/레버리지 설정 실패, 진입 주문 실패·미체결, 진입 확인 5회 실패, 익절 지정가 등록 실패(청산 후),
청산 수량 확인 불가 5회, 청산 확인 5회 실패, 익절 지정가 취소 5회 실패, 외부 청산 방식 OTHER, 모든 단계 소진(cycle=false),
선택할 패턴 없음, 거래량 급변 중지 예약 후 단계 종료. 비활성화 시 STOMP 알림(`autotrade.alert`)으로 화면 alert.

### 7. 화면 (chart.html)
- 상태 수신: STOMP `/user/queue/autotrade.status.{exchange}.{mode}.{symbol}` + REST `/api/autotrade/status`.
- 현재 블록 깜빡임(`block-current`), POSITION_HOLDING 시 "진입: x / 변동률: y%" 1초 갱신.
- 익절 지정가 대기(`tpOrderPending`) 시 leaf 블록 우측 상단 스피너(`block-order-pending`) + "익절 지정가 대기: {가격}".
- `holdingQueueIds`(보유 중 큐 ID 목록)로 끄기·삭제 확인 팝업 여부 판단.
- 큐 생성·수정 모달: "사이클 모드", "거래량 급변 시 중지" 토글(`.toggle-switch`).
- 큐 카드: 중지 예약 시 "⏸ 중지 예약" 뱃지(`volumeStopReserved`). 목록을 다시 불러올 때 반영됩니다.
- 마이페이지 투자 상세: 부분 익절 후 손절 건은 진입·매도(익절분)·청산(손절분) 3행과 `+X USDT 익절, -Y USDT 손절` 요약 줄을 표시합니다.
  행별 손익은 서버 계산 — 앞쪽 EXIT는 (체결가−진입가)×수량−자기 수수료−진입 수수료 배분, 마지막 EXIT는 투자 손익 − 앞쪽 합(합계가 투자 손익과 일치).

### 8. 알려진 한계
- **SIM은 지정가 부분 체결·미체결을 재현하지 못합니다.** 가격이 TP에 닿으면 전량 지정가 체결로 간주합니다.
- SIM은 시세를 약 0.1초 간격으로 받아 처리하므로, 실거래 지정가라면 체결됐을 순간 꼬리(wick)를 놓칠 수 있습니다.
- 진입 확인 대기(약 5초) 중 거래소 안전망 SL이 먼저 발동하면 "진입 미체결"로 판단할 수 있습니다 (매우 드묾, 이 경우에도 큐는 비활성화).
- 부분 익절 후 손절 판단(D1)은 레인 안 추정 손익 기준 — 합산 손익이 0 근처면 실제 부호와 다를 수 있습니다(이력은 실값 기록).
- 부분 익절 합산 투자 이력은 계산식 손익이며 펀딩비가 빠집니다.
- 큐 종료 요청 30초 대기 초과 시 오류를 응답하지만, 이미 실행 중인 레인 명령은 끝까지 진행될 수 있습니다(새로고침으로 상태 확인).
- 앱 재시작 시 보유 포지션·대기 지정가 상태는 메모리 기반이라 복구되지 않습니다 (거래소 안전망 TP/SL이 보호).
  시작 시 세션 자동 복구도 없으며, 사용자가 큐를 삭제·토글·수정할 때 세션이 처음 상태로 다시 만들어집니다.
  이때 거래소에 남은 포지션이 있으면 진입 직전 확인(3-3)으로 진입을 보류합니다. 남은 포지션의 정리는 안전망 TP/SL에 맡깁니다.
- 거래량 중지 예약이 남은 큐를 재시작 후 끄지 않고 **수정만** 하면, 처음부터 다시 돌다가 그 단계가 끝날 때 중지됩니다.
- "중지 예약" 뱃지는 실시간 갱신되지 않습니다 (세션 매매 로그의 `[중지 예약]` 줄은 실시간).
- 거래량 집계는 구독 시작부터라 앱 재시작·감시 시작 직후 60초는 판정하지 않습니다. 큐가 중지돼도 같은 세션에 다른 감시 큐가 남아 있으면 체결 구독은 유지됩니다.
- Binance 조건부 주문 이력 조회 범위 한계로 7일 넘게 보유 후 안전망 발동 시 청산 방식 판별 실패 → 큐 중단 가능 (손익은 정상 기록).

### G. 운영 중 알림이 오면 직접 확인할 상황
아래 메시지·알림이 보이면 **거래소의 포지션과 미체결 주문을 직접 확인**해 주세요.

- 진입 확인 5회 연속 실패 ("진입 확인 실패")
- 손절 전 익절 지정가 취소 5회 연속 실패 ("손절 중단")
- 외부 청산 후 남은 익절 지정가 취소 실패 ("거래소 미체결 주문을 수동으로 확인")
- 익절 지정가 등록 실패 후 "포지션 청산 미확인"
- 큐 끄기·삭제 시 "거래소 포지션 청산 미확인" 오류 (확인되면 큐는 자동 비활성화됨)
- 거래 이력에 `[이력 저장 실패] 체결은 완료됨` FAILED 행 → 거래소 내역과 대조
- **앱 재시작 후**: 보유 포지션·대기 지정가 추적이 끊기므로 거래소에 남은 주문·포지션 확인

- Binance 503 "Unknown error": 주문이 실제로 성공했을 수 있으므로 거래소에서 확인
